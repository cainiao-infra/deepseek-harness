# Increment B: admissible recovery verification

English | [中文](report.zh.md)

## Outcome and supported scope

Increment B resolves executable candidates before inference, publishes provider-declared failure handling, prevents unchanged persistent retries, and supports an explicit stop without a fictitious native plan. The [machine-readable record](summary.json) separates controlled decisions from live DeepSeek decisions. This is a fixed development pickup-scene diagnostic, not held-out or task-family acceptance; formal G1–G4 remain unaccepted.

The registered pickup program passed an additional zero-planner native trial with 110 actions. Its catalog matches increment A’s successful sparse-memory pickup catalog, and both enrollment revisions are reconstructed from the actual measured descriptors and provider skill source digests. The resolver recomputes their qualification manifests. Only whole-task `task-complete` is qualified; no intermediate manipulation stage is inferred from this outcome.

## Real simulator verification

The six controlled cases were assigned before execution, using the original provider, fixed pickup layout, original skill catalog and real RoboDojo physics. A test-owned worker raises a declared persistent sparse-policy incompatibility before its first action; native cleanup, runner stop acknowledgement, fresh observation and independent success evaluation remain unchanged. The recorded transport supplies one controlled decision through the shipped DSH profile and SDK. These cases establish runtime behavior, not model decision quality or naturally occurring failure recovery.

| Case | Expected behavior | Recorded result |
|---|---|---|
| Switch to qualified alternative | Exclude unchanged failed sparse policy; admit registered code program. | 110 actions; native success; one controlled call; one replacement. |
| No alternative | Stop before inference. | 0 actions; 0 calls; explicit no-candidate stop. |
| Unavailable candidate | Reject a proposal selecting the failed candidate. | 0 actions; one call; candidate ID rejected. |
| Stale observation identity | Reject the outdated decision. | 0 actions; one call; observation sequence rejected. |
| Explicit model stop | Stop without composition or operations. | 0 actions; one call; explicit stopped outcome. |
| Unknown mandatory predicate | Retain uncertainty and stop before inference. | 0 actions; 0 calls; undetermined condition retained. |

A separate live DeepSeek trial uses the ordinary credential-scrubbed official-provider gateway with the same pre-action fault, catalog, qualified alternatives and execution checks. It completed with one DeepSeek call, one Session, one replacement and 110 real actions; RoboDojo independently reported success. The evaluator measured 54.28 seconds including policy cold start, versus 48.96 seconds for the controlled switch; these two diagnostic episodes do not establish a latency comparison. Its provider receipts, exact requests/responses and durable Session are retained separately; a model answer alone never establishes task success.

Successful chains are independently audited against receipts, candidate digests, model-visible projections, committed revisions, binding identities, failure cleanup, stop/recapture ordering, every dispatched action and the terminal outcome. Negative cases intentionally terminate without task success and cannot pass the successful-chain audit. All assigned failures and unfinished attempts remain in the evidence denominator.

## Deployment failures and attribution correction

Earlier isolated batches retain metadata-protocol startup failures, a missing observation-sequence field at binding, and an absent Node executable on the remote process PATH. The implementations and startup environment were repaired before the final batch. Interrupted batches retain their complete frozen assignments and cleanup records; they are not counted as successful recovery tests. A separate changed-catalog qualification experiment retains one code success and one sparse failure, and is not merged into the original-catalog sparse qualification.

Source inspection also corrects increment A’s pi05 attribution: its restored physical trials used the original inference configuration because the launcher rebuilt `PYTHONPATH` with the default provider checkout. The transform patch was measured in separate fixed-observation probes only. Sparse-memory already has explicit transforms, so its measured pickup qualification is unchanged. Optional `physicalrsi_root` now validates and selects the provider before launch; a regression test checks the actual policy-process environment. Raw increment A outcomes remain unchanged.

## Evidence and limits

The [archive receipt](archive.json) identifies the complete retained archive and every imported file. It includes all experiment assignments, failed attempts, source snapshots, actual provider sources, qualification bundle, provider byte receipts, Session logs, native outcomes and process cleanup. Credentials are excluded. The [validation receipt](validation.json) records executed checks and any pre-existing repository failure. Repository evidence extracts permit scope and invariant checks; the archive retains full RGB/model payloads for complete reconstruction.

The demonstrated replacement starts after a zero-action fault, with both grippers open and reviewed guards. It does not qualify recovery after a partial grasp, unknown robot effects, or arbitrary stage restart. Checkpoint configuration and retained deployment inventories identify this fixed environment; the resolver does not hash live multi-gigabyte weight files on every decision. Qualification does not establish sparse-policy repeatability, and pi05, stacking and toolbox remain outside the verified recovery scope. Physical-device stopping, semantic progress monitors, three dependent subgoals, performance gains and formal comparisons belong to later increments.
